Changes are captured by a transactional database hook (a MongoDB change stream on employees and the designation, department, location and grade names). For each affected employee HRMS computes the published snapshot; only when it differs from the last one published does it write, in one transaction, an outbox event and the new snapshot. Saving an employee without changing a published field sends nothing. One server at a time runs the watcher, so event positions follow commit order. After downtime it resumes where it stopped; if that is impossible it rescans every employee, and the nightly reconciliation catches anything missed.

There is no message broker today. Both transports read the same outbox, and a Kafka or NATS publisher can be added later as a third reader with the same events.

Ordering and idempotency

  • Per employee: events of one employee_code arrive in sequence order on both transports. If you ever see a sequence lower than or equal to the one you hold, ignore it.
  • Overall: pos increases in commit order. Webhooks are sent in pos order and never skip: a failed event blocks the ones after it for that system until it succeeds.
  • Repeats: a delivery whose 2xx answer was lost is sent again. Keep the event_ids you processed (or compare sequence) and answer 2xx to a repeat.
  • Several changes made in one save produce one event. A rename of a designation, department, location or grade produces an EMPLOYEE_UPDATED for each employee who holds it.

Push: signed webhooks

An HR Admin adds your system in HRMS (Masters › Company › Integrations) with your HTTPS address and receives a signing secret once (whsec_…). HRMS then POSTs each event as the JSON body, with:

HeaderValue
Content-Typeapplication/json
X-HRMS-Event-IdThe event_id
X-HRMS-Event-TypeThe event_type (TEST for the Test button; ignore it after verifying)
X-HRMS-TimestampUnix seconds of this attempt
X-HRMS-Signaturesha256= + hex HMAC-SHA256(secret, timestamp + "." + raw body)

Answer any 2xx within 15 seconds once the event is stored on your side. Anything else, a redirect, or no answer counts as a failure: HRMS retries the same event after 10 s, 20 s, 40 s … up to once an hour, and sends nothing newer to you meanwhile. Pausing your system in HRMS keeps the events waiting; nothing is dropped. A system may ask for some event types only; the others are passed over.

Verifying the signature

// Go
func verify(secret string, r *http.Request, body []byte) bool {
  ts := r.Header.Get("X-HRMS-Timestamp")
  n, err := strconv.ParseInt(ts, 10, 64)
  if err != nil || math.Abs(float64(time.Now().Unix()-n)) > 300 {
    return false // stale or replayed
  }
  m := hmac.New(sha256.New, []byte(secret))
  m.Write([]byte(ts + "."))
  m.Write(body)
  want := "sha256=" + hex.EncodeToString(m.Sum(nil))
  return hmac.Equal([]byte(want),
    []byte(r.Header.Get("X-HRMS-Signature")))
}
# Python
import hmac, hashlib, time

def verify(secret: str, headers, body: bytes) -> bool:
    ts = headers["X-HRMS-Timestamp"]
    if abs(time.time() - int(ts)) > 300:
        return False  # stale or replayed
    want = "sha256=" + hmac.new(
        secret.encode(), ts.encode() + b"." + body,
        hashlib.sha256).hexdigest()
    return hmac.compare_digest(
        want, headers["X-HRMS-Signature"])

Verify over the raw body bytes exactly as received, before parsing the JSON. When the secret is rotated in HRMS, deliveries are signed with the new one at once.

Pull feed

Instead of (or as well as) webhooks, a system can read the outbox with an API key an HR Admin makes for it (hrmsk_…, shown once; HRMS stores only its SHA-256). Send it as Authorization: Bearer <key>. A missing, wrong or paused key gets 401.

GET /api/mdm/events?after=<pos>&limit=<n>        after ≥ 0 (default 0), limit 1–1000 (default 100)

200 {
  "events":     [ …events in pos order, pos > after… ],
  "next_after": 161,     // pass as after= next time (unchanged when the page is empty)
  "has_more":   true,    // ask again at once
  "head":       412      // the last pos written when the page was read
}

Store next_after only after you have processed the page. Poll every few seconds to a minute when has_more is false.

Snapshots for the nightly reconciliation

Each consumer compares its copy with HRMS's once a night (SOP §6). Same API key.

GET /api/mdm/employees/summary
200 { "schema_version": "v1", "count": 53,
      "checksum": "5277b6d3…",            // see below
      "algorithm": "sha256 of \"employee_code:sequence\\n\" per employee, in employee_code byte order",
      "head": 412, "generated_at": "2026-11-11T20:30:00.000Z" }

GET /api/mdm/employees?after=<employee_code>&limit=<n>     limit 1–1000 (default 200)
200 { "schema_version": "v1",
      "employees": [ { "employee_code": "EMP-1001", "sequence": 2, "hash": "…", "pos": 61, "data": { …snapshot… } }, … ],
      "next_after": "EMP-1200",   // null on the last page
      "has_more": true }
  1. Compute the checksum over what you hold: for each employee in employee_code byte order, the line employee_code:sequence\n; SHA-256 of all lines, hex. If count and checksum match, you are in step.
  2. Otherwise page through /api/mdm/employees and replace every employee whose sequence differs from yours. hash is the SHA-256 of the snapshot's canonical JSON (keys sorted), if you prefer to compare content.

HRMS runs its own reconciliation every night after 02:00 (Asia/Kolkata): it recomputes every employee's snapshot and publishes an event for any difference the watcher missed, so the feed itself stays complete.

Versioning policy

  • Adding a field to data is not a shape change: it stays v1. Ignore fields you do not know.
  • Removing, renaming or retyping a field is a shape change: the payload becomes v2, announced in advance. HRMS keeps sending each system the version it was set up for until it moves.
  • Consumers keep a translator for every version they have received, so old events in their stores stay readable (backward translation). HRMS does the same for the CMS's events.
  • Identifiers never change once assigned: an employee_code is never reused or renamed.

For the CMS team: property events HRMS accepts

CMS is the source of truth for property_id. HRMS keeps a read-only copy and links each HRMS location to its property once (the link never changes). A linked location's name follows the CMS name, and when the CMS deactivates a property, HRMS retires the location from that day (reason “Deactivated in the CMS”). An HR Admin can switch on “Properties come from the CMS”; new locations can then only be added by picking a CMS property.

Property list for HRMS's nightly reconciliation

When an HR Admin sets the CMS address (and optionally an API key), HRMS calls every night:

GET {base}/properties?limit=500[&cursor=<next_cursor>]
Accept: application/json
Authorization: Bearer <CMS API key>        // when one is set

200 {
  "properties": [
    { "property_id": "PROP-77", "name": "Gurugram 29 Hub", "city": "Gurugram", "state": "Haryana",
      "status": "Active", "updated_at": "2026-11-11T09:30:00Z" }
  ],
  "next_cursor": "opaque-or-null"            // null or "" on the last page
}

Every property, active or not, should be listed (deactivate, never delete). HRMS fixes any drift in its copy and in the linked locations, skips a property whose newer event already arrived after updated_at, and reports (without changing) properties it holds that the list no longer contains.

Setting it up in HRMS

HR Admin, Masters › Company › Integrations:

  • Add system for PMS, Purchase Desk and Moneyball: name, webhook address, event types, and whether to start from every event so far (first sync) or new events only. Copy the signing secret shown once. Test sends a signed TEST event.
  • Add API key for a system that pulls. Keys and secrets show their last four characters afterwards; New secret / New key replaces them at once.
  • CMS: Make CMS secret (give it to the CMS team), set the CMS address and key, and switch “Properties come from the CMS” on when every location is linked. Masters › Locations shows each location's CMS property and links an existing one.
  • Reconcile now runs the nightly check at once; the last runs are listed with what they fixed.

Secrets are stored sealed (AES-256-GCM) with the app's secret key, the same key that protects the Google Drive connection. Keep APP_SECRET (or the key file) safe and unchanged; if it changes, rotate every secret.
